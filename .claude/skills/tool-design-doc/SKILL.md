# 設計書作成（ツール設計ドキュメント作成）

ユーザーが新しいツール・アプリ・システム・自動化を作りたいと言ったとき、実装を始める前に、
Claude Code がそのまま実装に使える「設計書」を一緒に作るためのスキルです。

設計方法をゼロから毎回作り直さず、このファイルに書かれた進め方・質問の仕方・構成・チェック基準を
土台として使ってください。

**重要**：設計書を作っている間は、ユーザーから明確な許可が出るまでツールの実装を開始しないでください。

## いつ使うか

- 「〇〇するツールを作りたい」「〇〇を自動化したい」「こんなアプリが欲しい」と言われたとき
  → 実装前に一度だけ「設計書作成Skillを使って、先に設計書から整理しますか？」と確認し、同意された場合のみ使う
- 「設計書を作って」「仕様を整理して」「実装前に要件をまとめて」と明確に依頼されたとき
  → そのままこのスキルを使う

次のような小さな作業では提案しない。これらはそのまま直接対応する。

- 文言変更・色の変更など既存画面の小さな修正
- 原因がはっきりしている単純なバグ修正
- 数行で終わる単発スクリプト

## 進め方

### STEP 1：作りたいツールを確認する

まだ何を作りたいか聞いていない場合は、次のように質問する。

> 今、どのようなツールを作ってみたいですか？
> まだ詳しく決まっていなくても大丈夫です。
> 「こんなことをラクにしたい」という段階でも構いません。

回答を受け取ったら、次の3つに整理する。

- **すでに決まっていること**：ユーザーが明確に伝えた情報
- **仮定すれば進められること**：情報が不足しているが、一般的なおすすめ案を置けば初稿を作れる内容
- **実装前に確認が必要なこと**：判断によって機能・費用・安全性・データ構成が大きく変わる内容

### STEP 2：必要な情報だけ質問する

質問を機械的に全部行わない。今回のツールに必要な情報だけを選び、実装結果に大きく影響するものから確認する。

質問ルール：

- ユーザーがすでに話した内容は再質問しない
- 一度に質問するのは**最大3問まで**
- 専門用語を使う場合は短い説明を付ける
- 「どちらがいいですか？」だけで終わらず、必ずおすすめ案も示す
- 答えがなくても進められる内容は仮定して進める。仮定した内容は設計書内で明記する
- 質問だけを何度も続けず、できるだけ早く初稿を見せる
- 技術選定をユーザーが決められない場合は、運用しやすい案を提案する
- ユーザーが「お任せ」と言った場合は、理由付きで推奨案を採用し、できるだけ早く初稿に進む

確認が必要になりやすい項目の例：誰が使うのか／何をラクにしたいのか／現在どう作業しているか／
利用者が何を入力するか／最終的に何が出力されるか／PCかスマホか／ログインが必要か／
情報を保存する必要があるか／複数人で使うか／権限を分けるか／外部サービス連携／
個人情報・決済情報を扱うか／絶対に必要な機能・不要な機能／完成の判断基準／費用の上限

### STEP 3：設計書の初稿を作る

重要な情報がある程度そろったら、全部決まるのを待たずに初稿を作る。不足している情報は
「仮定」または「未決事項」として明記する。非エンジニアが読んでも分かり、同時に
Claude Code が実装に使える具体性を持たせる。

**標準構成**（全部無理に埋める必要はなく、今回必要な項目だけ選ぶ）：

1. ツール概要（名前・一言概要・目的・最小構成）
2. 背景と解決する問題
3. 対象利用者
4. 対象範囲（今回作るもの／あれば便利なもの）
5. 対象外
6. 利用の流れ（時系列）
7. 画面と操作
8. 機能要件（機能ごとに：目的・利用できる人・入力・処理・出力・エラー時の動作）
9. 入力と出力
10. データ設計（表形式推奨：データ名・内容・必須・保存先・閲覧できる人・削除方法）
11. 外部サービス連携
12. 利用者と権限
13. エラーと例外
14. 非機能要件
15. 技術構成案（推奨案＋別案＋理由、初心者が運用できるか、初期/月額費用、拡張時の注意点）
16. **完成条件**（チェックボックス形式。「使いやすい」等の曖昧表現は禁止、確認可能な基準にする）
17. **テストケース**（表形式：テスト名・事前条件・操作・期待される結果・確認方法。正常系・異常系・エラー系の最低3種）
18. **仮定**（Claudeが置いた仮の内容。決定事項として扱わない）
19. **未決事項**（実装前にユーザーが決めるべきこと。Claudeのおすすめも添える）
20. 実装の進め方（Phase分け。まだ実装は開始しない）

曖昧な言葉はそのまま書かず、確認可能な基準に変換する（例は本ファイル末尾の「曖昧語の変換例」を参照）。

### STEP 4：自己チェックする

ユーザーに見せる前に、以下を確認し、直せる問題は直してから見せる。

- 何を作るか・誰が使うか・何を解決するかが一文で説明できる
- 利用者の操作が時系列で分かる、入力・処理・出力が具体的
- 保存するデータ／しないデータ、閲覧・編集・削除できる人が分かる
- 入力不足・通信失敗・二重操作など失敗時の動作がある
- 完成条件が確認可能な形になっている、正常系・異常系・エラー系のテストがある
- 「いい感じ」「使いやすい」等の曖昧語が具体化されている、仮定と決定事項が分かれている

重要な情報が不足していて自己チェックで直せない場合だけ、追加で質問する。

### STEP 5：ユーザーの希望に合わせて調整する

初稿を見せた後、次のように確認する。

> この設計書を、今後どのような形で作りたいですか？
> もっと短くする、詳しくする、画面設計を増やす、質問を減らすなど、気になる点をそのまま教えてください。

修正を希望されたら反映する。

### 設計書を出す時の最後の確認

設計書の最後に、必ず次の3点を簡潔に示す。

- **今回決まったこと**（ユーザーの発言・合意で確定した内容）
- **Claudeが仮定したこと**（情報不足のため初稿のために仮置きした内容）
- **実装前に決めること**（実装結果に影響する未決事項）

最後に次のように聞く。

> この設計書を修正しますか？
> 問題なければ、次に実装計画へ進めます。まだ実装は開始しません。

### やってはいけないこと

- ユーザーが求めていない機能を大量に追加する
- すべての質問に回答が出るまで初稿を作らない
- 分からない内容を事実として断定する、仮定と決定事項を混ぜる
- 正常時だけを書いて終わる（失敗時の動作を書かない）
- 「使いやすい」「柔軟」「適切」などの曖昧語だけで済ませる
- 技術名を並べるだけで選定理由を書かない
- 設計書作成中に勝手に実装を始める

## 曖昧語の変換例

- 「使いやすくして」→ 1画面で主要操作が完了する／必須項目が分かる／実行中が分かる／
  エラー箇所が分かる／結果をコピーできる／スマホでも使える　等の確認可能な基準に変換
- 「自動化したい」→ 何をきっかけに動くか／どこから情報を取得するか／何を処理するか／
  どこへ結果を送るか／人間の確認を挟むか／失敗時に誰へ通知するか
- 「安全にして」→ ログイン／権限／データ暗号化／個人情報の保存範囲／APIキー管理／操作ログ／バックアップ／削除方法
- 「速くして」→ 何秒以内が目標か／どの処理が遅いか／待てる時間／処理中表示の要否／非同期処理にするか

## 実装計画・実装フェーズ

ユーザーが設計書に納得し「実装計画に進んで」と言ったら、20章の Phase 分けを具体的な作業リストに
展開する（まだコード実行や実際の構築はしない。作業の洗い出しのみ）。
ユーザーが明確に「実装（構築）して」と言って初めて、Phase 1 の範囲だけを実際に構築する。
Phase 2 以降は、未決事項（会費の金額・審査フローなど）が決まってから、あらためて設計書を作る。

## 個人の好み（このユーザー向けの設定）

ベースとなる設計書作成ルールとは別に、このユーザーと作業した実績から分かっている個人の好み。

- よく作るツールの傾向：小規模な団体・協会・会員管理系のツール（例：協会の会員・会費・認定管理）
- 技術に詳しくないため、専門用語は使う場合に短い説明を添える
- **技術構成の既定の推奨**：小規模な管理ツールは Google スプレッドシート＋Googleフォーム＋
  Google Apps Script を第一候補にする（初期費用・月額費用がほぼゼロ、Excel感覚で運用できる）。
  本格的な自社開発のWebアプリは、別案として理由付きで提示するが、既定の推奨にはしない
  （運用・保守の負担が大きいため）。ユーザーがより本格的な構成を希望した場合はそちらに従う。
- 質問は**最大3問**まで、かつテンポよく初稿に進める（このユーザーは要点だけ答えて次に進みたいタイプ）
- セクションを削る場合でも、**完成条件（16）・仮定（18）・未決事項（19）は必ず残す**
  （このユーザーはこの3つで「何が決まり、何がまだか」を把握している）
- 設計書はチャット内に直接Markdownで提示する（別途Googleドキュメントや専用ファイルにする必要はない。
  ユーザーが明示的に「ドキュメントにして」等求めた場合のみ別出力にする）
- 複数機能のツールは必ずPhaseに分割し、**最初はPhase 1（最小構成）だけを実際に構築する**。
  Phase 2以降は、未決事項が埋まってから改めて設計書を作る
